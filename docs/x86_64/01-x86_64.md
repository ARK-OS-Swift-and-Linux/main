# x86_64 Architecture in ArkOS

The x86_64 (AMD64) architecture is the legacy, yet overwhelmingly dominant, platform for desktop and server computing. ArkOS supports x86_64 primarily for QEMU testing and standard PC deployments.

## Boot Path Complexity

Unlike AArch64 which generally has a unified entry point (EL2/EL1), x86_64 suffers from decades of backward compatibility. ArkOS must handle two entirely different firmware environments:

### 1. Legacy BIOS (Basic Input/Output System)
The CPU starts in 16-bit Real Mode.
-   **Boot Sector:** The BIOS loads the first 512 bytes (`bootloader.asm`) at memory address `0x7C00`.
-   **Stage 1.5:** The bootloader must use BIOS interrupts (like `INT 13h`) to load `stage2.asm` from the disk.
-   **Protected Mode:** The bootloader switches the CPU to 32-bit Protected Mode, disabling BIOS interrupts permanently.
-   **Long Mode:** The bootloader sets up the PML4, PDP, PD, and PT page tables to identity-map the first few gigabytes of RAM, enables PAE (Physical Address Extension), and sets the LME (Long Mode Enable) bit in the EFER MSR (Model Specific Register) to finally enter 64-bit mode.

### 2. UEFI (Unified Extensible Firmware Interface)
The CPU is already in 64-bit Long Mode (or at least 32-bit Protected Mode).
-   **EFI Application:** The bootloader is compiled as a PE32+ Windows executable (the standard UEFI format).
-   **Boot Services:** ArkOS calls UEFI Boot Services to allocate memory, load the kernel (`bzImage`), and set the graphics mode via GOP (Graphics Output Protocol).
-   **ExitBootServices:** Before jumping to the Linux kernel, ArkOS must call `ExitBootServices` to take full control of the hardware.

## Kernel Interactions

ArkOS passes control to the Linux kernel using the standard x86 boot protocol. It constructs a `boot_params` structure in memory (the "zero page") containing the e820 memory map, the video mode parameters, and the address of the initramfs.
